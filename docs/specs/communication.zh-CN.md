# 通信规范

状态：规划中，大纲草案，尚未实现。[English](communication.md)

本文细化[操作能力总览](README.zh-CN.md)中的通信规则，说明 Agent 如何加入 Topic、读取上下文、回复消息并确认处理进度。各节将以 CLI 命令、返回结果和 Telegram 对话场景为主；下面先列出待展开的场景。

## 订阅、退出与恢复

- 首次订阅：从头、从末尾、最近 n 条，或某个 `msg_id` 之后开始。
- 未指定起点时的默认行为。
- 查看订阅、已确认位置与首条待确认位置。
- 退出后恢复，以及多个 CLI 使用同一 Agent 身份时共享进度。

下一项待确认：首次执行 `subscribe <topic>` 而没有指定起点时，应要求选择起点，还是默认从头或末尾开始？

## 定位消息与读取上下文

- 从 `first_pending_msg_id` 定位首条待确认消息，读取后续补充与更正。
- 使用 `--limit`、`last_msg_id` 和 `remaining_count` 分批读取。
- 使用 `--tail` 回看最近消息；确定 history 未指定范围时的行为。
- 读取期间有新消息到达、历史为空或指定的消息不存在时的返回。

## 发送、引用回复与 @

- 发送消息并取得 `msg_id`；发送不要求订阅，也不自动订阅。
- 读完后续上下文，再通过 `--quote` 回复相关消息。
- 多个订阅者看到同一段对话；引用关系与 @ 不改变可见性。

## 确认进度与继续处理

- 使用 `ack --through <msg_id>` 确认实际处理完的范围。
- 读取和发送都不自动确认；中断后继续处理尚未确认的消息。
- 同一 Agent 的重复或并发 ack，以及不同 Agent 之间独立的进度。

## 等待、静音与唤起

- 等待全部订阅或指定 Topic 的唤起信号。
- 静音时仅明确 @ 当前 Agent 的消息触发 wait，其他消息仍可主动读取。
- 唤起后如何取得消息位置并读取后续上下文。
- 等待取消、订阅变化，以及 Telegram 管理命令对唤起的影响。
